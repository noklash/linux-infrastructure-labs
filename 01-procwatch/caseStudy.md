# ProcWatch: Reconstructing Linux Process Monitoring from `/proc`

## A Systems Engineering Project in C

**Project:** ProcWatch
**Language:** C
**Platform:** Linux
**Interface:** `/proc` pseudo-filesystem
**Build system:** GNU Make
**Compiler:** GCC (GNU Compiler Collection)
**Purpose:** Build a lightweight process-monitoring utility that reconstructs process information directly from the Linux kernel's `/proc` interface.

---

# 1. Project Overview

ProcWatch is a Linux systems programming project that explores how process-monitoring tools such as `ps`, `top`, and `htop` obtain and present process information.

Instead of invoking those utilities, ProcWatch reads the Linux `/proc` pseudo-filesystem directly.

The project was deliberately designed around a simple systems-engineering question:

> **What does it actually take to reconstruct process information from the interfaces Linux exposes to userspace?**

The result is a command-line process monitor capable of:

* Enumerating running processes.
* Reading process metadata directly from `/proc`.
* Reading process command lines.
* Calculating CPU utilization from successive samples.
* Sorting processes by CPU utilization.
* Sorting processes by memory usage.
* Inspecting individual processes.
* Displaying process hierarchy.
* Inspecting open file descriptors.
* Inspecting memory mappings.
* Handling processes that disappear while being inspected.
* Building multiple C source files through a Makefile.
* Separating process collection, parsing, calculation, display, and utility functions into different modules.

The project also became an exercise in debugging low-level systems code.

Several problems occurred during development, including:

* GNU Make indentation errors.
* Incorrect Makefile target formatting.
* A mismatch between `Makefile` and `makefile`.
* Incorrect C library feature exposure for `usleep()`.
* Missing standard-library declarations for `exit()`.
* Incorrect `/proc/[pid]/stat` field parsing.
* Misinterpretation of enormous virtual memory values.
* `sscanf()` format warnings.
* `snprintf()` truncation warnings.
* Understanding the difference between compiler warnings and build failures.
* Comparing ProcWatch's output against Linux's own `ps` implementation.

Those failures were not incidental. They were part of the engineering work.

---

# 2. Engineering Objective

The objective was not simply to produce a program that displays processes.

The deeper objective was to understand the layers involved:

```text
Linux kernel
     │
     │ exposes process state
     ▼
/proc pseudo-filesystem
     │
     │ userspace reads files
     ▼
C program
     │
     ├── discovers PIDs
     ├── reads /proc/<pid>/stat
     ├── reads /proc/<pid>/cmdline
     ├── parses kernel-provided fields
     ├── stores process state
     ├── samples again
     ├── calculates CPU usage
     ├── sorts processes
     └── displays results
```

This makes ProcWatch more than a CLI exercise.

It is a small example of how userspace software interacts with kernel-provided interfaces.

---

# 3. Why `/proc`?

Linux exposes a large amount of kernel and process information through `/proc`.

It is commonly called a pseudo-filesystem because its contents are generated dynamically by the kernel rather than representing ordinary persistent files on disk.

For example:

```text
/proc/1/stat
/proc/1/status
/proc/1/cmdline
/proc/1/fd/
/proc/1/maps
```

For a process with PID `3011`:

```text
/proc/3011/stat
/proc/3011/cmdline
/proc/3011/fd/
/proc/3011/maps
```

ProcWatch uses these interfaces as its data source.

This creates a useful architectural boundary:

```text
Kernel
  │
  ▼
/proc
  │
  ▼
ProcWatch
```

ProcWatch does not need to understand the internal kernel data structures directly.

It consumes the userspace interface Linux provides.

# 6. The Build System

The project uses GNU Make.

The core variables are:

```make
CC      = gcc

CFLAGS  = -std=c11 -Wall -Wextra -Wpedantic -O2 -g

LDFLAGS =

SRC_DIR = src

OBJ_DIR = obj

BIN     = procwatch

SRCS = $(SRC_DIR)/main.c $(SRC_DIR)/proc.c $(SRC_DIR)/display.c $(SRC_DIR)/util.c

OBJS = $(SRCS:$(SRC_DIR)/%.c=$(OBJ_DIR)/%.o)
```

The important idea is that source files are compiled separately into object files:

```text
main.c     → main.o
proc.c     → proc.o
display.c  → display.o
util.c     → util.o
```

Then they are linked:

```text
main.o
proc.o
display.o
util.o
   │
   ▼
procwatch
```

This is different from compiling everything into one giant command.

# 7. Makefile Troubleshooting

The first build failure was:

```text
makefile:17: *** missing separator.  Stop.
```

This is one of the classic GNU Make errors.

The problem was caused by recipe lines that were not formatted as Make expects.

For example:

```make
$(BIN): $(OBJS)

    $(CC) $(CFLAGS) -o $@ $^ $(LDFLAGS)
```

Make requires recipe commands to begin with a literal tab.

The correct form is:

```make
$(BIN): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^ $(LDFLAGS)
```

The same applies to:

```make
$(OBJ_DIR)/%.o: $(SRC_DIR)/%.c | $(OBJ_DIR)
	$(CC) $(CFLAGS) -c $< -o $@
```

and:

```make
$(OBJ_DIR):
	mkdir -p $(OBJ_DIR)
```

and:

```make
clean:
	rm -rf $(OBJ_DIR) $(BIN)
```

### Lesson

GNU Make is indentation-sensitive in a very specific way.

Normal spaces are not interchangeable with the tab that begins a recipe.

A useful diagnostic is:

```bash
cat -n makefile
```

For more precise inspection:

```bash
sed -n '14,30l' makefile
```

The latter can expose tabs and trailing characters.

# 8. Another Makefile Problem: `Makefile` vs `makefile`

The project used:

```text
makefile
```

rather than:

```text
Makefile
```

When:

```bash
cat -n Makefile
```

was executed, the system returned:

```text
cat: Makefile: No such file or directory
```

But:

```bash
cat -n makefile
```

worked.

Linux filenames are case-sensitive.

Therefore:

```text
Makefile
makefile
MAKEFILE
```

are three different filenames.

GNU Make can recognize lowercase `makefile`, so this was not inherently a problem for `make`.

The important lesson was filesystem case sensitivity.

# 9. The "No Rule to Make Target" Error

After correcting the indentation, the next error was:

```text
make: *** No rule to make target 'obj/main.o', needed by 'procwatch'.  Stop.
```

The source files existed:

```text
./src/main.c
./src/proc.c
./src/display.c
./src/util.c
```

but the Makefile's pattern rule was malformed because the target and recipe had been placed on the same line.

The intended rule was:

```make
$(OBJ_DIR)/%.o: $(SRC_DIR)/%.c | $(OBJ_DIR)
	$(CC) $(CFLAGS) -c $< -o $@
```

This rule tells Make:

> An object file such as `obj/main.o` can be produced from `src/main.c`.

The `%` is a pattern.

Therefore:

```text
obj/main.o
```

matches:

```text
obj/%.o
```

and the corresponding source becomes:

```text
src/main.c
```

### Lesson

A Makefile is a dependency graph.

It is not simply a list of shell commands.

The build system needs to know:

```text
what depends on what
```

and:

```text
how to produce each target
```

# 10. First C Compilation Problem: `usleep()`

After the Makefile was corrected, compilation reached `main.c`.

The compiler reported:

```text
error: implicit declaration of function ‘usleep’;
did you mean ‘sleep’?
```

The code contained:

```c
usleep((useconds_t)(interval * 1e6));
```

The source had:

```c
#define _POSIX_C_SOURCE 200809L
```

The issue is that `usleep()` is obsolete in modern POSIX specifications and its declaration may not be exposed when requesting the 2008 POSIX API.

The engineering lesson here was important:

> Including `<unistd.h>` does not guarantee that every function associated with that header will be declared under every feature-test configuration.

Feature-test macros affect which interfaces headers expose.

The better modern approach is to use `nanosleep()` for this type of interval.

For example:

```c
struct timespec req;

req.tv_sec = (time_t)interval;
req.tv_nsec = (long)((interval - req.tv_sec) * 1e9);

nanosleep(&req, NULL);
```

This avoids relying on obsolete `usleep()` behavior.

# 11. Missing `exit()` Declaration

Another compilation failure occurred in `util.c`:


The compiler explicitly suggested:

```text
include ‘<stdlib.h>’
```

The file contained:

```c

```

but lacked:

```c
#include <stdlib.h>
```

The fix was straightforward.

### Lesson

In C, the compiler needs a declaration before using a function.

The standard library function:

```c
exit()
```

is declared in:

```c
<stdlib.h>
```

This is one reason strict compiler options are valuable:

```text
-Wall
-Wextra
-Wpedantic
```

They make missing declarations and questionable code much easier to detect.

```c
double timeval_diff_sec(const struct timespec *a,
```

# 13. `/proc/<pid>/stat`

The most important debugging problem occurred in the process parser.

Linux provides a large amount of process information through:

```text
/proc/<pid>/stat
```

For example:

```bash
cat /proc/3011/stat
```

returned:

```text
3011 (code) R 2866 2863 2863 0 -1 4194368 1027310 0 9436 0 35083 4665 0 0 0 20 0 12 0 9909 1558849155072 93127 ...
```

The fields are positional.

Relevant fields include:

```text
1   pid
2   comm
3   state
4   ppid
14  utime
15  stime
20  num_threads
22  starttime
23  vsize
24  rss
```

This makes parsing dangerous.

A single skipped field causes every field after it to become misaligned.

# 14. The First Parser Bug

The first implementation produced output such as:

```text
VSIZE 18014398509481983k
RSS   384539735670784k
```

These values were obviously suspicious.

For example:

```text
18014398509481983
```

is far outside the expected virtual memory range of a normal desktop process.

The initial parser was skipping the wrong number of fields.

The relevant portion originally looked conceptually like:

```c
%lu %lu
%*d %*d %*d %*d %*d %*d
%d %*d
%llu %lu %lu
```

After reading:

```text
utime
stime
```

the parser skipped too many fields.

That shifted:

```text
num_threads
starttime
vsize
rss
```

onto the wrong values.

# 15. Diagnosing `/proc` Parsing

Rather than guessing, the raw kernel interface was inspected directly:

```bash
cat /proc/3011/stat
```

For PID `3011`, the important portion was:

```text
... 20 0 12 0 9909 1558849155072 93127 ...
```

Mapping the fields:

```text
18 priority
19 nice
20 num_threads
21 itrealvalue
22 starttime
23 vsize
24 rss
```

Therefore:

```text
num_threads = 12
starttime    = 9909
vsize        = 1558849155072
rss          = 93127
```

The parser needed to skip exactly the correct number of fields.

After `stime`:

```text
16 cutime
17 cstime
18 priority
19 nice
```

Then:

```text
20 num_threads
21 itrealvalue
22 starttime
23 vsize
24 rss
```

This produced the corrected format.

# 16. The Corrected Parser Logic

The relevant format became:

```c
int n = sscanf(
    rest,
    "%c %d "
    "%*d %*d %*d %*d %*u "
    "%*lu %*lu %*lu %*lu "
    "%lu %lu "
    "%*ld %*ld %*ld %*ld "
    "%d %*d "
    "%llu %lu %ld",
    &state,
    &ppid,
    &utime,
    &stime,
    &num_threads,
    &starttime,
    &vsize,
    &rss
);
```

The important thing was not memorizing the format string.

The important thing was understanding its relationship to the kernel's field numbering.

---

# 17. Why `comm` Requires Special Handling

There is another subtle problem with `/proc/<pid>/stat`.

The second field is:

```text
comm
```

and it is enclosed in parentheses.

For example:

```text
3011 (code) R ...
```

The process name can contain spaces and parentheses.

Therefore blindly tokenizing the entire line by whitespace is unsafe.

The implementation instead finds the closing parenthesis:

```c
const char *rparen = strrchr(buf, ')');
```

Then finds the opening parenthesis:

```c
const char *lparen = strchr(buf, '(');
```

The process name is extracted from the region between them.

This demonstrates a general systems-programming lesson:

> Kernel interfaces often have compact formats with special parsing rules. You need to understand the format before choosing a parsing strategy.

After fixing the parser, ProcWatch produced:

```text
PID     PPID    STATE THR       VSIZE      RSS   CPU% COMMAND
------- ------- ----- ------ -------- -------- ------ ----------------

1811    1484    S     20     3935652k  161072k  12.0% ...
```

The next step was not to assume these numbers were correct.

They were compared against Linux's `ps`:

```bash
ps -p 3011 -o pid,comm,vsz,rss,nlwp
```

Result:

```text
    PID COMMAND            VSZ   RSS NLWP
   3011 code            1522314604 366000 13
```

And:

```bash
ps -p 1811 -o pid,comm,vsz,rss,nlwp
```

Result:

```text
    PID COMMAND            VSZ   RSS NLWP
   1811 gnome-shell     3946468 169088 20
```

This comparison provided an independent sanity check.

The values were close because the processes were live and the measurements occurred at different moments.

The thread count for PID 3011 also changed:

```text
ProcWatch: 12
ps:        13
```

This is expected because processes can create and destroy threads dynamically.

# 19. Important Lesson: Huge VSZ Does Not Necessarily Mean Huge RAM Usage

At one point the output contained:

```text
VSIZE 1522315612k
RSS   345900k
```

The VSIZE appeared enormous.

It would have been easy to conclude that the parser was broken.

The raw `/proc` value showed:

```text
vsize = 1558849155072 bytes
```

Converting to KiB:

```text
1558849155072 / 1024
≈ 1522315616 KiB
```

This matched the ProcWatch output.

Therefore the large value was real.

The important distinction is:

### Virtual memory size

`vsize` represents the process's virtual address space.

It does not mean that all of that memory is physically resident in RAM.

### RSS

RSS means Resident Set Size.

It represents memory pages currently resident in physical memory.

Therefore a process can have:

```text
large VSIZE
small RSS
```

without anything being wrong.

This was one of the most important conceptual lessons of the project.

---

# 20. RSS Is Reported in Pages

Another important detail is that `/proc/<pid>/stat` reports RSS in pages.

For PID 3011:

```text
rss = 93127
```

Assuming a 4 KiB page size:

```text
93127 × 4096
≈ 381 MB
```

`ps` reported:

```text
RSS = 366000 KiB
```

The exact observed value can differ because the processes are live and measurements are taken at different times.

The project therefore reinforces another systems concept:

> Raw kernel interfaces do not always expose values in the same units that human-facing tools display.

A systems engineer needs to know both:

```text
what the kernel reports
```

and:

```text
what the user interface represents
```

# 21. CPU Utilization

CPU percentage cannot be calculated from a single `/proc/<pid>/stat` snapshot.

The process's CPU time is cumulative.

ProcWatch therefore takes two samples:

```text
Sample A
   │
   │ wait
   ▼
Sample B
```

For each process:

```text
CPU time at B
      -
CPU time at A
      =
CPU consumed during interval
```

The relevant fields are:

```text
utime
stime
```

where:

* `utime` is CPU time spent executing user code.
* `stime` is CPU time spent executing kernel code on behalf of the process.

Total CPU time:

```text
utime + stime
```

---

# 22. Clock Ticks

Linux reports process CPU time in clock ticks.

ProcWatch obtains the number of clock ticks per second through:

```c
sysconf(_SC_CLK_TCK);
```

The helper:

```c
long get_clk_tck(void)
```

caches this value.

The CPU calculation is conceptually:

```text
delta_ticks
     /
clock_ticks_per_second
     =
CPU seconds consumed
```

Then:

```text
CPU percentage =
CPU seconds consumed
/
wall-clock sample interval
× 100
```

The sample interval is measured using:

```c
clock_gettime(CLOCK_MONOTONIC, ...)
```

Using `CLOCK_MONOTONIC` is important because CPU measurement should not depend on changes to the system wall clock.

---

# 23. Why Two Samples Are Required

Suppose:

```text
utime + stime = 1000 ticks
```

at the first sample.

At the second sample:

```text
utime + stime = 1050 ticks
```

Then:

```text
delta = 50 ticks
```

If:

```text
CLK_TCK = 100
```

then:

```text
50 / 100 = 0.5 seconds
```

of CPU time were consumed.

If the sampling interval was:

```text
1 second
```

then:

```text
0.5 / 1 × 100
= 50%
```

So the process used approximately 50% of one CPU during the sample.

This is fundamentally different from simply reading a "CPU percentage" field from the kernel.

ProcWatch derives the metric.

---

# 24. CPU Percentage Is a Measurement

This is a useful systems-thinking lesson.

ProcWatch does not receive:

```text
CPU = 14%
```

from `/proc/<pid>/stat`.

It receives raw cumulative counters.

It then derives:

```text
CPU%
```

from:

```text
counter difference
+
time difference
```

This is the same general pattern used throughout observability systems:

```text
raw cumulative metric
        ↓
sample
        ↓
sample again
        ↓
calculate delta
        ↓
normalize by time
        ↓
derive rate
```

The same idea appears in:

* network byte rates,
* disk I/O rates,
* request rates,
* packet rates,
* system counters,
* monitoring systems.

# 25. Process Tables

ProcWatch stores process information in:

```c
struct proc_table
```

The table contains:

```text
count
capacity
procs
```

The process records are stored as:

```c
struct proc_info
```

This separates:

```text
one process
```

from:

```text
the collection of processes
```

The table initially allocates space for:

```text
512 processes
```

If the table becomes full, `ensure_capacity()` doubles the capacity up to `MAX_PROCS`.

The important concept is dynamic storage.

Instead of assuming:

```text
there will always be exactly 100 processes
```

the program can grow its internal collection.

# 26. Process Discovery

ProcWatch opens:

```c
opendir("/proc");
```

It then iterates through directory entries:

```c
readdir(dir)
```

But `/proc` contains more than process directories.

Examples include:

```text
/proc/sys
/proc/meminfo
/proc/cpuinfo
/proc/filesystems
```

Processes are represented by numeric directory names:

```text
/proc/1
/proc/2
/proc/3011
/proc/6650
```

Therefore ProcWatch uses:

```c
is_pid_dir()
```

to check whether a directory name consists entirely of digits.

This produces:

```text
/proc
  │
  ├── sys       → ignore
  ├── meminfo   → ignore
  ├── cpuinfo   → ignore
  ├── 1         → process
  ├── 2         → process
  ├── 3011      → process
  └── 6650      → process
```

# 27. Race Conditions With Processes

One subtle Linux behavior is that processes are dynamic.

A process may exist when:

```c
readdir()
```

returns its PID.

But by the time ProcWatch tries:

```text
/proc/<pid>/stat
```

the process may have exited.

Therefore:

```c
if (proc_read_one(pid, p) == 0)
    t->count++;
```

silently skips processes that disappeared.

This is intentional.

It is not necessarily an error.

This is a practical lesson in concurrent systems:

> The state you observe can become invalid immediately after you observe it.

The program therefore treats process disappearance as a normal race rather than crashing.

# 28. Command-Line Arguments

Linux exposes a process's command line through:

```text
/proc/<pid>/cmdline
```

Unlike ordinary text files, command-line arguments are separated by NUL characters.

Conceptually:

```text
program\0argument1\0argument2\0argument3\0
```

The helper:

```c
read_file_null_sep()
```

converts those separators into spaces for human-readable display:

```text
program argument1 argument2 argument3
```

This is another example of adapting a kernel interface into a user interface.

# 29. Kernel Threads

Some entries displayed by ProcWatch look like:

```text
kworker/R-rcu_gp
kworker/R-sync_wq
migration/0
ksoftirqd/0
rcu_preempt
```

These are kernel threads.

Their command lines can be empty.

ProcWatch therefore falls back to the process name when `/proc/<pid>/cmdline` is unavailable or empty.

This is why output such as:

```text
kworker/R-netns
```

can still be displayed meaningfully.

# 30. Sorting

ProcWatch supports:

```bash
./procwatch
```

which defaults to CPU sorting.

It also supports:

```bash
./procwatch --top memory
```

The implementation uses the C standard library's:

```c
qsort()
```

Two comparison functions are provided:

```c
cmp_cpu()
cmp_mem()
```

The CPU comparator sorts highest CPU usage first.

The memory comparator sorts highest RSS first.

This demonstrates a useful C pattern:

```text
data structure
+
comparison callback
+
qsort()
```

# 33. Error Handling

ProcWatch defines:

```c
die()
```

and:

```c
warn()
```

`die()` prints an error and terminates.

Example:

```text

```

`warn()` prints a warning while allowing execution to continue.

This creates a simple distinction:

```text
fatal problem
     ↓
die()

recoverable problem
     ↓
warn()
```

This is better than scattering raw `fprintf()` calls throughout the entire codebase.

# 35. Compiler Warnings Are Not Automatically Build Failures

One of the most useful practical lessons was seeing output such as:

```text
warning: ...
```

followed by:

```text
gcc ... -o procwatch ...
```

and ultimately a successful build.

A warning means:

> The compiler found something questionable or potentially problematic.

An error means:

> The compiler could not produce the requested object file.

The project experienced both.

For example:

```text
error: implicit declaration of function ‘usleep’
```

stopped compilation.

By contrast:

```text
warning: ‘%s’ directive output may be truncated
```

did not stop compilation.

Engineering discipline means understanding the difference.

A successful build does not necessarily mean a warning should be ignored forever.

# 36. `sscanf()` Warnings

After the parser was corrected, GCC reported:

```text
warning: use of assignment suppression and length modifier together in gnu_scanf format
```

The format contained patterns such as:

```c
%*lu
```

The `*` means:

```text
assignment suppression
```

The value is parsed but not stored.

The `l` is a length modifier.

The warning demonstrates an important property of C's formatted-input functions:

> `scanf()` family format strings have complicated type and conversion rules.

The parser was functionally working, but the compiler was still telling us that the format string deserved attention.

This warning should eventually be eliminated by making the skipped conversions use appropriate standard conversion specifications without unnecessary length modifiers, or by replacing the highly positional `sscanf()` approach with a more robust parser.

That is a future refinement rather than a reason to discard the current architecture.

---

# 37. `snprintf()` Truncation Warning

The compiler also reported:

```text
warning: ‘%s’ directive output may be truncated
```

for:

```c
snprintf(
    linkbuf,
    sizeof(linkbuf),
    "/proc/%d/fd/%s",
    pid,
    ent->d_name
);
```

The buffer was:

```text
256 bytes
```

but GCC determined that the possible resulting path could exceed that size.

`snprintf()` is safer than `sprintf()` because it respects the destination buffer size.

However, truncation can still be undesirable.

The correct engineering response is not:

> Ignore the warning because the program still runs.

Instead:

```text
understand the maximum expected input
        ↓
choose an appropriate buffer
        ↓
check the return value
        ↓
handle truncation explicitly if necessary
```

This warning remains a cleanup item in the project.

# 41. Lessons From C

The project reinforced several fundamental C concepts.

## Headers provide declarations

If a function is used:

```c
exit()
```

the appropriate header must expose its declaration.

## Types matter

C does not perform the same automatic type conversions and runtime checks common in higher-level languages.

Formatted input is especially sensitive to type mismatches.

## Memory must be managed explicitly

The process table uses:

```c
calloc()
realloc()
free()
```

The programmer owns the lifecycle.

## Pointers matter

Functions such as:

```c
proc_find()
```

return pointers to structures stored inside the process table.

Understanding pointer lifetime is essential.

## Static functions create internal module boundaries

For example:

```c
static int parse_stat(...)
```

means the function is private to that translation unit.

This is useful for keeping implementation details out of the public interface.

# 42. Lessons From Linux

The project provided several deeper Linux lessons.

## `/proc` is an interface

It provides userspace access to kernel-maintained information.

## Processes are dynamic

A PID can disappear at any time.

## Process information is not one single object

Different files expose different dimensions:


A huge virtual address space does not imply equivalent RAM consumption.

## CPU utilization is derived

The kernel exposes counters.

Monitoring software derives rates and percentages from them.

## Kernel interfaces have precise formats

A parser must respect field numbering and units.

# 51. Engineering Principle: Never Trust Your First Interpretation

One of the most valuable lessons from this project was the temptation to interpret an unexpected number immediately.

When ProcWatch displayed:



```text

      ↓

      ↓

      ↓
convert units
      ↓

      ↓
```

That distinction matters.

Systems engineering requires separating:

```text

```

from:

```text
incorrect
```

They are not the same thing.

# 58. Final Lessons

ProcWatch started as a relatively simple question:

> How can I list Linux processes without calling `ps`?

The implementation exposed much deeper concepts.

A process is represented by kernel-maintained state.

Linux exposes that state through interfaces such as `/proc`.

Userspace software reads those interfaces.

The software must understand:

```text
format
types
units
lifetime
concurrency
sampling
```

before it can turn raw kernel data into useful information.

The most important lessons from the project were therefore:

1. **A Linux system is full of interfaces. Learn to inspect them directly.**

2. **`/proc` is not just a directory full of files. It is a kernel-to-userspace interface.**

3. **Parsing positional kernel data requires extreme attention to field numbering.**

4. **A single parsing error can shift every subsequent field and produce apparently impossible values.**

5. **Unexpected values should be investigated against the raw source before being declared incorrect.**

6. **Virtual memory and physical memory are different concepts.**

7. **CPU utilization is commonly derived from cumulative counters and elapsed time.**

8. **Live systems are changing while you inspect them. Race conditions are normal.**

9. **Compiler warnings are valuable engineering information even when the build succeeds.**

10. **A build system is part of the software, not an afterthought.**

11. **Independent verification against existing system tools is essential.**

12. **Good systems engineering is often about understanding boundaries: kernel to `/proc`, `/proc` to parser, parser to data model, and data model to presentation.**
